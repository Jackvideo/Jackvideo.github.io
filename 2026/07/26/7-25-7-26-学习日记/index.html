学习情况

这两天主要在系统学习企业级 Agent / AI 应用中的 RAG 架构与检索链路。

之前对 RAG 的理解还比较停留在“向量库 + 大模型问答”这个层面，但这次顺着架构分层、Chunk、Embedding、Vector Search、Hybrid Search 一路梳理下来，感觉已经逐渐形成了一条比较完整的学习主线。

RAG 不是简单的向量库问答

这次首先重新明确了 RAG 系统的定位。

RAG 并不是简单地把文档丢进向量库，然后让大模型问答。更准确地说，它是一套围绕外部知识获取、索引、检索、排序、上下文构建和可信生成的完整工程系统。

从 Agent 开发视角来看，RAG 更应该被设计成一个可调用的 Knowledge Tool。也就是说，Agent 在执行任务时先判断是否需要外部知识，如果需要，再调用 RAG 工具获取结构化证据，而不是每次都无脑检索。

这样一来，RAG 就不只是“补知识”的模块，而是 Agent 系统里负责知识访问、证据组织和可信回答的重要能力。

企业级 RAG 的架构分层

在架构上，我把 RAG 系统拆成了几个层次来理解：

层次 主要职责
知识接入层 文档解析、清洗、切片、元数据提取
索引构建层 向量索引、关键词索引、摘要索引
知识存储层 向量库、关键词索引库、元数据、原文对象存储
检索运行层 查询理解、混合检索、过滤、重排序、上下文构建、引用溯源
生成层 基于证据回答、依据校验、兜底处理
Agent 集成层 把 RAG 封装成 Agent 可调用的工具
评估与运维层 效果评估、日志、trace、成本、反馈、权限审计

这样拆完之后，RAG 的工程复杂度就清楚很多了。它不是一个单点组件，而是一条从“知识进入系统”到“模型生成回答”的完整链路。

企业级场景尤其要关注权限、版本、溯源和评估。否则即使模型回答看起来很流畅，也可能引用了过期文档、错误版本，甚至未授权内容。

Chunking：构造可检索的知识单元

接着重点学习了 Chunk 切分策略。

Chunking 的目标不是把文本平均切小，而是构造可检索、可追溯、可授权、可用于生成的知识单元。一个企业级 chunk 不应该只是裸文本，而应该包含：

也就是说，一个 chunk 既要有正文内容，也要知道自己来自哪里、属于哪个文档、哪个版本、有什么权限要求，以及在生成回答时如何引用回原文。

常见切分策略包括：

策略 特点
固定长度切分 实现简单，但容易切断语义
递归结构切分 按标题、段落、句子、token 逐级降级
语义切分 根据相邻文本单元的语义变化切分
层级切分 保留章节、段落、小块之间的父子关系
上下文增强切分 给小块补充标题、摘要、来源等上下文

其中我觉得比较重要的是 parent-child chunking。小 chunk 用于精准召回，父 chunk 用于补全上下文。这样既能保证检索足够精确，又不至于让模型拿到一段过碎、缺上下文的内容。

Embedding 与 Vector Search

Embedding 的本质，是把离散文本映射到连续高维向量空间里，让语义关系可以通过几何距离来计算。

Embedding 生成的是稠密向量，大多数维度都有非零值；每一维不是人工定义的某个词，而是模型学习出来的分布式语义特征。相比之下，BM25、one-hot、词袋模型这类方法属于稀疏表示，更适合精确词匹配。

BM25 与 RRF

BM25 这块主要学习了它的三个核心部分：

部分 含义
IDF 词越稀有，区分度越高，权重越大
词频饱和 一个词出现越多越重要，但重要性不会无限线性增长
文档长度归一化 避免长文档因为词多而天然占优

其中 k1 控制词频增长时的饱和速度，b 控制长文档受到长度惩罚的程度。

BM25 在 RAG 中的价值，是补足向量检索对精确词面信号不敏感的问题。比如用户问某个错误码、接口名、产品型号、合同条款编号时，BM25 往往比纯向量召回更稳。

多路召回之后，就需要融合排序。这里学习了 RRF，也就是 Reciprocal Rank Fusion。
